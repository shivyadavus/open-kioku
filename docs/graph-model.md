# Graph Model

Node types include files, directories, modules, packages, classes, traits, interfaces, functions, methods, fields, endpoints, tables, queues, topics, configs, tests, build targets, runtime errors, tickets, pull requests, and architecture components.

Edge types include `CONTAINS`, `DEFINES`, `REFERENCES`, `CALLS`, `IMPLEMENTS`, `EXTENDS`, `IMPORTS`, `DEPENDS_ON`, `DERIVED_FROM`, endpoint edges, config reads/writes, table reads/writes, event publish/consume, `TESTS`, ownership, change, failure, and ticket relationships.

Every edge carries evidence:

- extractor source
- source type
- file path and line range when available
- symbol id when available
- confidence
- optional numeric confidence score and reason
- optional freshness label
- indexed timestamp

`DERIVED_FROM` links a file to the file it is produced from or exists to exercise or
describe: a generated module and the modular source its banner names, a test and the module
it tests, a `.d.ts` and its implementation. The edge runs from the derived file to its
origin and is built at index time by `open-kioku-ingest::derived`, one per derived file:

| Derivation (`properties.derivation`) | Evidence | Confidence | Proof |
| --- | --- | --- | --- |
| `declared-origin` | the file's own header (`automatically generated from <path>`, first eight lines). The named path must resolve **as written from the root or relative to the generated file** — never by searching the index for the basename, which fires precisely when the header is wrong — and must not climb above the root | High, `static_analysis` | `declared_origin`; corroborating, never authoritative |
| `test-pairing` | file-name convention: `foo_test.go`, `foo.test.ts`/`foo.spec.ts`/`foo_test.ts` (also from a `__tests__/` folder), `test_foo.py`/`foo_test.py`, `FooTest.java`/`FooTests.java`/`FooIT.java`; same directory first, then a mirrored tree (`tests/pkg/test_x.py` ↔ `src/pkg/x.py`, `src/test/java/p/XTest.java` ↔ `src/main/java/p/X.java`) when exactly one non-test file fits | Medium, `heuristic` | none; the edge stays heuristic |
| `declaration-pairing` | `foo.d.ts` beside `foo.ts`/`.js` | Medium, `heuristic` | none |

A convention that could mean two files (`loader.py` in two packages, a test that mirrors
neither) emits nothing rather than a guess, and a generated file whose banner names no file
(`Code generated by protoc-gen-go. DO NOT EDIT.`) is flagged generated but has no origin edge.
**No derived edge is ever authoritative.** A generation banner is a claim a comment makes about
its own file, and `likely_generated` — the prose match that finds it — was calibrated for a
ranking demotion where a false positive costs one rank. Every authoritative proof kind in this
workspace comes from parsed structure, so `declared_origin` caps at corroborating and a
naming-convention pairing, which has no proof at all, stays heuristic. A path-similarity rule
was tried as a way to promote banners and removed: substring containment matches `io` inside
`session`, and "same directory" promotes any two neighbours, which is exactly where fixture and
`gen/` trees put spurious banners. Nothing machine-checkable is available at index time, so
nothing is promoted. In practice this means a generated file appears in `possible_impact` and
never in `proven_impact`.

Two consumers read the edge. Impact walks it in the derived -> origin direction only, so
editing an origin surfaces what is derived from it (`ok impact`, MCP `impact_analysis`) while
editing a generated file does not claim to affect its source; both arrive as labeled
possibilities — a declared origin carrying its `declared_origin` proof kind so a reader can tell
it from a naming guess, and neither ever as proven impact. Retrieval reads it from either end and admits the other side of a candidate into
the context pack with the edge as evidence (`docs/ranking.md`, `derived:<edge>`).

No untyped graph read returns it. `neighbors` — which backs `module_dependencies` — and
`shortest_path`, which backs `dependency_path`, both exclude it in the SQLite and in-memory
stores, and it is kept out of a context pack's `dependency_edges`: a test does not depend on the
module it is named after, so it must not become a hop in anything a caller reads as a dependency
chain. Consumers that want the edge ask for it by type.

Test selection is deliberately not wired to it: `find_tests_for_change` already pairs a test
to its subject by the same file-stem convention, and a `test-pairing` edge carries no proof,
so it could not raise a test above `Optional` anyway.

Nodes and edges also support additive metadata fields. `properties` stores
structured queryable facts that are specific to the node or edge family, such as
qualified names, route names, relation kinds, package names, or resolver output.
`schema_version`, `source_pass`, `index_mode`, and `extractor_version` record
where a fact came from. `ambiguity` and `quality_notes` preserve uncertainty and
quality caveats instead of flattening inferred facts into unsupported certainty.

All of these fields are backward-compatible serde defaults on the wire: an MCP or
`--json` consumer that has not seen a field still deserializes, and the serialized shape of
a `GraphEdge` is unchanged by the 4.0 storage work.

The graph builder creates file-to-symbol `DEFINES` edges from extracted symbols and `REFERENCES` edges from persisted exact symbol occurrences. Heuristic reference expansion is intentionally avoided for common repeated names; richer reference coverage should come from configured SCIP indexes or future language-specific resolvers. SQLite persists `graph_nodes` and `graph_edges`, and `open-kioku-storage::GraphStore` exposes neighborhood and shortest-path traversal to CLI and MCP callers.

`graph_nodes` keeps the full node JSON as the source of truth, with query columns
maintained for common filters:

- `graph_nodes.node_type`
- `graph_nodes.file_id`
- `graph_nodes.symbol_id`

`graph_edges` does not. Since 4.0 an edge is stored as typed columns plus integer
references into a per-table string dictionary, because the JSON document duplicated the
columns beside it and re-stated a handful of distinct paths, pass names and messages once
per edge. Endpoints and evidence strings are dictionary references (`from_sid`, `to_sid`,
`source_sid`, `ev_path_sid`, `ev_symbol_sid`, `ev_message_sid`, `ev_indexed_at_sid`), the
filterable types stay inline (`edge_type`, `confidence`, `source_type`, `freshness`), and
only fields with no column of their own land in a residual document. See
[Storage Model](storage-model.md#compact-graph-tables) for the layout, the measurements
behind it, and how a pre-4.0 index is detected and rebuilt.

Node schema migrations remain additive and idempotent. The edge layout is not
forward-migratable: opening a pre-4.0 index discards its edge rows and reports that
`ok index` must rebuild them, rather than reading them as an empty graph.
